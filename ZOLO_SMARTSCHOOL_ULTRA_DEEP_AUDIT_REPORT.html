🔴 Critical Security Vulnerabilities & Technical Fixes (What Needs to Be Done)

1. Sanctum API Tokens Never Expire (Indefinite Lifespan) Critical — High Severity

File: PHP_CODE/config/sanctum.php:47
Flaw: 'expiration' => null. In Laravel Sanctum, when expiration is null, Personal Access Tokens never expire. Once a student, parent, or staff member logs into a mobile device, that Bearer token remains valid indefinitely, even months or years later, or if the device is lost/stolen.

Remediation Code: 
// config/sanctum.php:47
// Expire tokens after 30 days (43200 minutes)
'expiration' => env('SANCTUM_TOKEN_EXPIRATION', 60 * 24 * 30),

// In app/Console/Kernel.php: schedule pruning of expired tokens daily:
$schedule->command('sanctum:prune-expired --hours=24')->daily();
2. MySQL Strict Mode Disabled on Both Connections High Severity — Data Integrity

File: PHP_CODE/config/database.php:59, 76
Flaw: 'strict' => false on both mysql and school tenant connections. Disabling strict mode allows MySQL to silently truncate oversized data, accept invalid zero-dates (0000-00-00), and execute non-standard GROUP BY queries with unpredictable aggregation results.

Remediation Code: 
// config/database.php:59 & 76
'strict' => true, // Enforces STRICT_TRANS_TABLES, NO_ZERO_IN_DATE, ERROR_FOR_DIVISION_BY_ZERO
3. Payment Gateway Secret Keys Stored in Plaintext in Database High Severity — Financial Security

File: PHP_CODE/app/Models/PaymentConfiguration.php:13-25
Flaw: The PaymentConfiguration model lacks an Eloquent $casts property. Stripe Secret Keys (sk_live_...), Razorpay Secret Keys, Paystack Secret Keys, and Webhook Secrets are stored in plaintext MySQL columns. Any database dump, backup leak, or SQL query exposure reveals all live payment secrets.

Remediation Code: 
// app/Models/PaymentConfiguration.php
protected $casts = [
    'api_key'            => 'encrypted',
    'secret_key'         => 'encrypted',
    'webhook_secret_key' => 'encrypted',
];
// Run a one-time migration to encrypt existing rows using Crypt::encryptString()
4. Arbitrary SQL Execution via Backup Restore (`DB::unprepared()`) Critical Severity — Remote Takeover

File: PHP_CODE/app/Http/Controllers/DatabaseBackupController.php:677, 839
Flaw: When restoring a database, the controller splits uploaded SQL strings and executes each query verbatim: DB::statement("SET FOREIGN_KEY_CHECKS = 0"); DB::unprepared(trim($query));. Any user with backup access can upload an SQL file containing GRANT ALL ON *.* TO ..., admin password overwrites, or MySQL UDF execution payloads.

Remediation Code:

Restrict backup restoration strictly to files generated internally on the server (validated via HMAC signature). Reject arbitrary uploaded .sql files, or run restoration exclusively via CLI with strict superadmin shell authorization.

5. XML File Upload Vector (XXE / SSRF Exposure) Medium / High Severity

File: PHP_CODE/app/Services/UploadService.php:20 & AssignmentController.php:96
Flaw: xml is explicitly listed in ALLOWED_EXTENSIONS. If an XML file containing external DTD references (<!ENTITY xxe SYSTEM "file:///etc/passwd">) is uploaded and parsed by any backend library or viewed in a browser, it risks XXE and SSRF.

Remediation Code: Remove 'xml' from UploadService::ALLOWED_EXTENSIONS and validation rules.
6. CORS Allowed Origins Defaults to Wildcard (`*`) Medium Severity

File: PHP_CODE/config/cors.php:25
Flaw: 'allowed_origins' => explode(',', env('CORS_ALLOWED_ORIGINS', '*')). When CORS_ALLOWED_ORIGINS is unset, any external website can make API calls to this server on behalf of a victim.

Remediation Code: Default to env('APP_URL') instead of '*'.
7. Heavy Mass-Assignment Surface (300+ `$request->all()` Calls & Missing FormRequests) Medium Severity

Scope: Across 75 web controllers and 6 API controllers, over 300 instances of $request->all() are passed into models or services. There is not a single FormRequest class in app/Http/Requests. If any model accidentally leaves a column un-guarded, malicious parameters can be injected.

Remediation Code: Migrate critical admission, fee, user profile, and payroll controllers to dedicated FormRequest classes with strict $request->validated() calls.

⏰ 6. Intelligent Timetable Matrix Engine & Multi-Standard Architecture

Deep Algorithmic Analysis
The User's Real-World Institutional Challenge:

"for example, if a teacher takes the maths in 11th and 12th for each section, and in some classes he can take chemistry class too. sometimes he even go to 10th class as well. so a teacher can attend any standard with any section, so we need to make an intelligent time table matrix to build a timetable without hassle."

1. How the Current System Works vs. Why It Struggles

Our inspection of Timetable.php, SubjectTeacher.php, TimetableGeneratorService.php, and TimetableGenerationService.php reveals:

  • Data Layer Capability: In the database, a teacher can already be assigned to multiple subjects across multiple classes and sections via SubjectTeacher (class_section_id, subject_id, teacher_id). For example, Teacher A (Mr. Sharma) can legitimately teach Maths in 11-A, Maths in 11-B, Maths in 12-A, Chemistry in 11-A, and Science in 10-A. The database schema fully supports this!
  • The Problem with V1 Generator: The V1 generator (TimetableGeneratorService.php) operates on a single class section at a time using a randomized shuffle($queue) greedy allocator. If you generate Class 11-A first, Teacher A is locked into Monday Period 1. When you subsequently generate Class 11-B or 12-A, Teacher A collides, gets rejected, and the generator either inserts an alternate teacher or fails to place the lecture! Generating class-by-class creates unavoidable scheduling deadlocks.
  • The State of V2 Generator: In September 2026, a deterministic backtracking constraint solver (TimetableGenerationService.php) was written that accepts an array of class_section_ids. However, the Web UI in edit.blade.php is strictly scoped to one class section URL (/timetable/{class_section_id}/edit). An administrator has no UI to trigger school-wide simultaneous generation!
  • Missing Global Visibility: There is no Master Cross-Class Teacher Matrix where a principal can view all teachers as rows and all school periods as columns to see who is teaching where in real time.

2. Architecture of the Intelligent Master Timetable Matrix

To solve the user's challenge without hassle, the timetable system requires three interconnected layers:

Visual Concept: Master Teacher Schedule Matrix (School-Wide View)

Instead of editing class-by-class, the principal opens the Master Teacher Matrix. Each row is a teacher; columns are days and periods. Overlaps are physically impossible because each cell represents a teacher's single physical location.
